# 插件审核标准

官方插件市场只收审核过的插件。审核读全部源码，并在审核用的主控上实际装上运行。下面每条都有编号，审核结论按编号指出问题。

## 一、必须满足（不满足就退回）

### A. 可审、可装

- **A1 源码可读**：提交的是可读源码。不接受混淆、压缩或加密过的代码；不接受运行时从网络下载代码再执行（`eval`、`new Function` 执行远程内容等）。
- **A2 依赖可查**：随包带的第三方代码写明名称、版本和来源（`package.json` 或 README 里列出），能对上公开发布的版本；不带原生扩展。
- **A3 能装能跑**：开发者模式能装上不报错；开启、关闭、重新开启都正常；`start` 15 秒内返回。
- **A4 身份**：`id` 不以 `dstatus-` 开头，不和已上架插件重名；每次投稿 `version` 都比上一版高。

### B. 权限与数据

- **B1 权限最少**：每个申请的权限都用得上，投稿单逐项写明用途。用不到的权限、页面、工具要删掉。
- **B2 出站有据**：`net:outbound:<host>` 只声明真正要访问的主机；README 与投稿单写明访问哪些外部服务、发出去什么数据、为什么。
- **B3 数据不外流**：节点信息、IP、设置、密钥、存储内容只用于说明里的功能，不发到说明以外的地方。不内置统计、广告、远程开关或「打电话回家」。
- **B4 秘密不露**：Token 之类只放 `ctx.secrets`；页面、日志、接口和工具返回里不出现完整秘密；`ui/` 目录里不放数据与秘密。

### C. 行为得体

- **C1 关掉就停**：关闭后没有定时器、没有出站请求、没有遗留的后台工作。
- **C2 频率相称**：定时间隔与用途相称（访问外部服务不要每分钟一次）；同一件事的通知有去重，不刷屏；日志不刷屏，正常运行时只记必要的事。
- **C3 写操作可控**：写入类工具声明 `dryRun` 并在预览里写清将要发生什么；页面里的删除、覆盖操作有确认。
- **C4 出错看得懂**：错误带 `code` / `errorCode` 和中文说明；上游失败、没配置、参数错能区分开，不伪装成功。
- **C5 不碰无关的事**：功能与插件说明一致，没有说明里没提到的隐藏功能。

### D. 说明与外观

- **D1 README**：写清做什么、每个权限的用途、怎么配置、存哪些数据、访问哪些外部服务（写法看 `template/README.md`）。
- **D2 界面中文**：界面文字、通知、错误信息用中文，说人话。
- **D3 外观一致**：页面用设计套件（`kit.css`），不写死颜色；亮色、暗色主题都能看；手机宽度不横向溢出。

## 二、建议（不挡上架）

- 改了存储结构时 `dataVersion` +1 并提供 `migrate`。
- AI 工具的 `title` 与入参 `title` 写成站长看得懂的中文。
- `start` 里把「什么数据都没有」当正常情况处理（新装、清空数据后都会遇到）。
- 外部服务暂时不可用时保留上次结果并标明时间，不清空页面。

## 三、审核怎么做

1. 按投稿单里的提交取源码，从头读到尾，对照上面各条。
2. 在审核用的主控上用开发者模式装上：按 README 走一遍主要功能，开关一次，看日志。
3. 写结论：**通过** / **需修改**（逐条写编号、问题、位置）/ **不通过**（写原因）。
4. 通过后，官方按投稿的那个提交原样打包签名、收进插件市场；不会替你改代码。

## 四、上架之后

- 更新同样投稿，只审这一版和上一版的差异；新增权限、出站目标与数据结构变化重点看。
- 上架后发现违反 A1、B2、B3、B4、C5，官方撤回该版本：已装的主控会停用它并通知站长。
